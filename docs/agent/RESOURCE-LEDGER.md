### 采取的节制措施

1. `images/`（11 GB）与 `catalog/products/`（8.3 GB）**不进 Git、不复制**，
   `.gitignore` + rsync 排除双重保险。
2. 本地**不执行 `pnpm install`**，依赖树只存在于服务器。
3. 商品图片不在本地重新生成衍生副本：轻量变体在服务器由 `tools/build_media.py` 产出，
   本地只负责把 `catalog/products/<PID>/processed/`（只读）传到服务器。
4. 原型 34 MB 截图只保留一份，不产生重复截图。
5. 未下载任何浏览器自动化环境；小程序验收改用**静态自检脚本**。

#### 关于 CPU 上限的一次实测修正

首次实测（T5 早期版本，未加限制）得到 **CPU 峰值 925%（9.25 核）、内存 3074 MB**，
**超出了目标文档「构建任务最多 4 CPU 核」的上限**。
修正方式：在 `infra/scripts/build.sh` 中用 `taskset -c 0-3` 把整个构建绑定到 4 个核上
（不是依赖工具自身的并行度参数，避免与 pnpm/vite 的线程池相互干扰）。

复测结果：**CPU 峰值 311%（3.11 核）、内存峰值 1756 MB**，两项均在预算内，
构建总耗时 73 s（限核前后基本持平）。

## 3. 待办与风险

| 项 | 说明 |
| --- | --- |
| 日常测试服务核数 | 目标文档要求「日常测试服务：总计最多 2.5 CPU 核、4GB 内存」。当前 compose 限额为 MySQL 2C + API 2C = 4C，超过 2.5 核；**需把 MySQL 降到 1C、API 保持 2C**，或停用 MySQL 容器时仅保留 API 的 2C。待在下一轮 compose 调整中落实。 |
| Docker 构建缓存 | 服务器既有 208.4 GB 构建缓存（**不属于本项目**）。本项目未新增构建层，也**未执行任何全局清理**，避免影响其他项目。 |
| 服务器磁盘 58% | 距 20% 阈值仍有 38 个百分点余量，但既有项目的构建缓存占比较高；本项目不再申请额外磁盘。 |
| 小程序预览 | 微信开发者工具不在本 WSL 环境，**无法在本机闭环验证**。已用静态自检脚本覆盖结构性问题，真机/模拟器验收需在 Windows 侧执行。 |
