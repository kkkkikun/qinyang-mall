### 采取的节制措施

1. `images/`（11 GB）与 `catalog/products/`（8.3 GB）**不进 Git、不复制**，
   `.gitignore` + rsync 排除双重保险。
2. 本地**不执行 `pnpm install`**，依赖树只存在于服务器。
3. 商品图片不在本地重新生成衍生副本：轻量变体在服务器由 `tools/build_media.py` 产出，
   本地只负责把 `catalog/products/<PID>/processed/`（只读）传到服务器。
4. 原型 34 MB 截图只保留一份，不产生重复截图。
5. 未下载任何浏览器自动化环境；小程序验收改用**静态自检脚本**。

#### 关于 CPU 上限的一次实测修正

首次实测（T5 早期版本，未加限制）得到 **CPU 峰值 925%（9.25 核）、内存 3074 MB**，
**超出了目标文档「构建任务最多 4 CPU 核」的上限**。

修正方式：在 `infra/scripts/build.sh` 中用 `taskset -c 0-3` 把整个构建绑定到 4 个核上
（不是依赖工具自身的并行度参数，避免与 pnpm/vite 的线程池相互干扰）。

**两次修正过程**（保留记录，便于复查）：

| 版本 | 遗漏点 | CPU 峰值 |
| --- | --- | --- |
| 限核 v1 | `pnpm install` 未被 taskset 包裹 | 311%（偶发 550%，install 步骤失控） |
| 限核 v2（当前） | install / contracts / typecheck / test / api / admin-web **全部**包裹 | **320%（3.20 核）** |

复测结果：**CPU 峰值 320%（3.20 核）、内存峰值 1626 MB**，两项均在预算内，
构建总耗时 75 s（限核前后基本持平）。

#### 第二次实测修正（引入「流水线内独立 API 实例」之后）

全量流水线新增了一个**本次构建产物的独立 API 进程**（端口 18112），
供页面级执行验证使用。首次实测时该进程**没有被 taskset 包裹**，
CPU 峰值升到 **700%（7 核）**，超出「构建任务最多 4 CPU 核」的上限。

修正：独立 API 进程同样用 `taskset -c 0-3` 包裹。
复测结果：**CPU 峰值 335%（3.35 核）、内存峰值 1629 MB、耗时 102 s**，
两项资源均在预算内；流水线退出码 0。
