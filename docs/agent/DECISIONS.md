## D-001 基线采用原型 v2

- **背景**：目标文档提到原型有 (1) 与 (2) 两个版本，要求比较差异并记录实际采用的基线。
- **决策**：工作区实际只有 `docs/reference/qinyang_customer_demo_v2_pixel.html`（v2），不存在 (1)。
  基线采用 **v2**，并以 `prototype/`（已按 v2 复刻并通过 100/100 浏览器用例）作为可直接执行的对照物。
- **理由**：没有 (1) 就无从比较；`prototype/` 已完成 17 项 ref 差异对齐，是 v2 的高保真落地。
- **影响**：视觉验收以 `prototype/` + `ref/` 53 张截图双基线。
- **复审**：若客户后续提供 (1)，需重新比对并记录差异。

## D-002 Git 远程仓库为公开仓库，同步仍走命令

- **背景**：目标文档要求「优先使用已经配置好的私有 Git 远程仓库」；用户答复「可以新建公开的 GitHub 仓库，
  但是服务器无法访问外网，所以还是需要用那个命令同步过去」。
- **决策**：
  1. 在已登录的 `kkkkikun` 账号下创建 **公开** 仓库 `qinyang/mall`（实际名 `qinyang-mall`），
     作为源码的对外存档与备份。
  2. **服务器同步仍以命令为主**：`infra/scripts/sync-to-server.sh`（rsync over SSH），
     唯一允许的同步入口，且同步后服务器持有完整 `.git`，构建以**固定 commit** 为准。
- **实测补充**：核对时发现服务器**实际可以**访问 GitHub（`git ls-remote` HTTPS 与 SSH 均成功），
  只有 `registry.npmjs.org` 直连被拒；npm 走 `registry.npmmirror.com` 镜像。
  尽管如此仍按用户要求以命令同步为主，把 GitHub 定位为**存档**而非构建依赖。
- **影响**：服务器构建不依赖外网可达性；本地与服务器用同一份提交历史。
- **复审**：若后续希望服务器直接 `git pull`，已具备条件（远端已配置且可达）。

## D-003 服务器运行时使用隔离的 Node 24

- **背景**：目标文档指定 Node.js 24 LTS；服务器系统 Node 为 22.21.1。
- **决策**：把官方 Node **24.22.3（LTS "Krypton"）** 安装到 `~/tools/node-v24.22.3`，
  通过 `PATH` 注入使用，**不改动系统 Node**，不影响服务器上其他项目。
- **理由**：既满足 24 LTS 要求，又不污染共享环境；卸载只需删除该目录。
- **影响**：所有 `infra/scripts/build.sh` 调用显式前置 `export NODE_HOME=~/tools/node-v24.22.3`。
- **复审**：无。

## D-004 依赖安装在服务器完成，本地不装依赖树

- **背景**：目标文档红线「禁止在本地安装完整 API/后台依赖树」「禁止本地部署 Docker/MySQL」。
- **决策**：`pnpm-lock.yaml` 在**服务器**生成并回写仓库；本地只写代码、跑 Python 脚本。
- **理由**：本地磁盘预算（新增 ≤ 8GB，目标 ≤ 10GB 上限）与「本地零重型依赖」的红线。
- **影响**：本地无法即时类型检查，迭代回路为「改码 → 同步 → 服务器 typecheck」。
  为压缩回路，同步脚本已做到「一条命令 + 服务器一次 typecheck」≈ 90 秒。
- **复审**：无。

## D-005 商品一律「仅报价」模式，价格恒为 null

- **背景**：76 件商品的名称、价格、材质、尺码、库存均未经商家确认。
- **决策**：V1 全部商品 `pricingMode = QUOTE_ONLY`，`priceCents = null`。
  API 层强制：`QUOTE_ONLY` 商品提交任何价格都会被 `normalizePrice` 拒绝。
  前端价格位显示金色「待报价」。
- **理由**：目标文档「未确认价格不能显示虚假价格」「不得编造商品经营数据」。
- **影响**：`FIXED_PRICE` 分支已实现（整数分入库、以元输入），待商家确认固定价商品后启用。
- **复审**：商家确认可直售商品清单后，为对应商品切 `FIXED_PRICE` 并填真实价格。

## D-006 商品种子数据为 DRAFT，不自动上架

- **背景**：「未经授权，不将商品资料自动发布」。
- **决策**：种子脚本写入的商品状态为 `DRAFT`。上架必须通过
  `POST /admin/products/:id/status`（**仅店主**）显式操作，并写审计日志。
  P1 垂直切片的验收脚本会**以真实 API 调用**完成一次上架，既验证链路又满足「显式操作」要求。
- **影响**：数据库初始状态无已发布商品；演示数据需先跑验收脚本。
- **复审**：商家确认可发布清单后，可批量执行同一流程。

## D-007 顾客身份：抽象 Provider + 开发期 mock

- **背景**：无微信 AppID / AppSecret，真实 `code2session` 无法调用；
  而目标文档禁止「修改旧小程序账号、AppID」。
- **决策**：定义 `CustomerIdentityProvider` 抽象，两个实现：
  - `WechatIdentityProvider`：真实 `jscode2session`（需商家授权的 AppID/Secret，**不写入仓库**）。
  - `MockIdentityProvider`：`WECHAT_MOCK_AUTH=true` 时启用，`code` 形如 `dev:openid-001`。
  由 `WECHAT_MOCK_AUTH` 环境变量切换，业务层零改动。
- **影响**：开发与测试可完整跑通顾客闭环；拿到 AppID 后改一个环境变量即可切换。
- **复审**：拿到合法 AppID 时切换为正式 Provider，并在 `docs/agent/DECISIONS.md` 追加一条变更记录。

## D-008 支付：接口 + 明确禁用的适配器

- **背景**：目标文档「V1 默认不启用真实微信支付」「禁止假支付成功、伪造已支付状态或生成虚假退款记录」。
- **决策**：`PaymentGateway` 抽象接口 + `DisabledPaymentGateway`。
  任何调用抛 `PAYMENT_DISABLED`；管理端 `POST /admin/orders/:id/pay` 返回 **409 PAYMENT_DISABLED**，
  同时只写一条 `status = DISABLED` 的事实记录（便于审计「为何没有支付流水」）。
  管理后台与小程序**都不出现**「去支付 / 已支付 / 退款」按钮。
- **影响**：不存在任何伪造支付或退款状态。
- **复审**：商家批准线上收款后，需单独确定「全款 or 定金」「尾款怎么结」「运费/取消退款谁核准」，
  再新增实现类与回调验签、幂等、查单补偿。

## D-009 金额一律整数分

- **决策**：所有金额字段以 `*Cents` 结尾，`int unsigned` 存储，禁止浮点。
  管理后台以「元」输入，提交前换算为分。
- **理由**：浮点累加会产生分位误差，定制单金额需与报价快照严格一致。
- **影响**：报价、订单、支付记录全程整数分；`totalCents = amountCents + freightCents` 由服务端计算。

## D-010 报价与订单快照在服务端冻结

- **决策**：创建报价时把商品与量体**快照**写入 `quotes`；生成订单时从报价继承快照写入 `orders`。
  后台之后修改商品，不影响既有报价与订单。
- **理由**：目标文档「订单确认后，不能因为后台修改商品而改变历史订单」。
- **影响**：订单详情展示的是下单时的商品与量体，与商品表当前值无关。

## D-011 报价版本化与顾客确认校验

- **决策**：
  - 同一申请同时只有一个 `ACTIVE` 报价版本，创建新版本时旧版本转 `SUPERSEDED`。
  - 顾客确认时后端校验三件事：报价属于该申请、`status === ACTIVE`、`version === expectedVersion`。
    任一不符返回 409（`QUOTE_NOT_ACTIVE` / `QUOTE_VERSION_CONFLICT`）。
  - 报价可被店主撤回（`WITHDRAWN`），申请回到 `PENDING_QUOTE`。
- **理由**：目标文档要求「报价变更必须生成新版本」「后端必须检查其确认的是否为当前有效版本」。
- **影响**：顾客在报价被改价后拿到旧版本确认会被明确拒绝，不会静默按旧价成交。

## D-012 状态机集中定义在共享契约

- **决策**：`REQUEST_STATUS_TRANSITIONS` 与 `ORDER_STATUS_TRANSITIONS` 定义在
  `packages/contracts`，API 的服务层直接复用同一份表，不各自维护。
- **理由**：三端（API / 后台 / 小程序）对状态的理解必须一致；集中定义后单元测试可直接覆盖。
- **影响**：非法迁移统一返回 409 `INVALID_STATUS_TRANSITION`，前后端提示语一致。

## D-013 量体模板版本化

- **决策**：模板按 `code` + `version` 组织，同一 `code` 同时只有一个 `ACTIVE`。
  已发布模板**不可原地修改**；再次发布生成新版本，旧版本转 `ARCHIVED`。
  历史申请保存 `templateId + templateVersion + 完整 sections 快照`。
- **理由**：目标文档「量体模板应支持版本化和后续调整」「未获得商家确认的测量字段不能作为不可修改的最终业务规则」。
- **影响**：商家调整必填项不会破坏历史申请的回溯能力。

## D-014 量体数据校验在服务端强制

- **决策**：提交申请时服务端按模板校验：必填项齐全、数值落在 `min/max` 区间、
  单位与模板一致（`cm` / `kg`，不接受顾客自行换算）、**模板外的字段一律拒绝**。
- **理由**：量体资料直接决定制版，不能依赖前端校验。
- **影响**：越界或缺项返回 400 `MEASUREMENT_INVALID`，并指出具体缺哪几项。

> **2026-11-26 复审补充**：本条决策本身正确，但**一度没有被真正执行**——
> 模板以原型 snake_case 入库时，服务端校验器读到的字段表是空的，
> 于是「必填齐全 / 越界拒绝 / 模板外字段拒绝」三条规则同时失效。
> 现已由 D-025 的形状归一化 + 单一解析入口修复，
> 并由集成测试与小程序端到端执行桩双重锁定。

## D-015 隐私：最小采集、订单归属校验、日志脱敏

- **决策**：
  - 只采集业务必需的姓名/电话/地区/详细地址与量体数据。
  - 顾客接口校验订单与申请归属本人，越权一律返回 **404**（不泄露存在性）。
  - 异常过滤器**只记录方法、路径、状态码与业务码**，绝不记录请求体。
  - 审计日志对 `contact` / `measurements` / `phone` / `address` 等键做 `[REDACTED]` 脱敏。
  - 顾客资料接口只返回手机号掩码。
- **理由**：目标文档「量体资料、联系方式、收货地址属于需要严格保护的数据」。
- **影响**：排障时需借助 `x-request-id` 而非日志正文定位请求。

## D-016 图片存储抽象 + 本地受控文件存储

- **决策**：`StorageService` 抽象；V1 只实现 `LocalFileStorageService`（含路径穿越防护）。
  `STORAGE_DRIVER=oss` 未实现时**启动即报错**，不静默降级。
- **理由**：目标文档「图片存储采用抽象接口，测试环境优先使用受控文件存储，正式环境再接商家授权的对象存储」。
- **影响**：正式接对象存储时新增一个实现类即可，业务层不感知。

## D-017 商品图片流水线在服务器执行

- **决策**：仓库内 `tools/build_media.py` 作为**权威流水线**，在服务器上用独立 venv（`~/tools/media-venv`）执行。
  只处理首批 13 件白名单商品的 `processed/`，输出 `media/products/<PID>/<IMGID>-{4x5,1x1,thumb}.jpg`。
  原始 `images/` 与 `catalog/products/` 不修改、不复制。
- **理由**：目标文档「必要的批量图片处理」由服务器承担；`catalog/display` 单张 4.3 MB 对小程序过重，
  需重生成 1200px / 600px 的轻量版本（`processed` 3.6 GB → `media` 约 50 MB）。
- **影响**：本地磁盘仅 +623 MB 传输中转（服务器侧），本地不新增副本；
  小程序列表与详情都直接使用 `media/` 下的 `4x5` 变体。

## D-019 管理后台与小程序在服务器类型检查，但本机无浏览器验收

- **决策**：后台（Vue 3 + Vite + TDesign）与小程序（原生 TS）均按「本机不装依赖」的约束编写，
  由服务器 `pnpm typecheck` 与 `build` 校验；小程序额外做**静态自检脚本**
  （页面清单与 `app.json` 一致性、资源路径越界检查、API 路径与契约一致性）。
- **理由**：目标文档禁止本地安装完整依赖树，也禁止为此下载浏览器自动化环境。
- **影响**：微信开发者工具预览与真机验收需在 Windows 侧执行，步骤已写入交付文档；
  **这是目前唯一无法在本环境闭环验证的环节**，已在 `docs/PROJECT-BASELINE.md` B2 记录。

> **2026-11-26 复审补充**：小程序没有 `package.json`（原生小程序不引入 npm 依赖），
> 因此**并不在 `pnpm -r typecheck` 的覆盖范围内** —— 17 个页面从未被类型检查器看过。
> 现已补上 `pnpm typecheck:miniprogram` 并接入 `build.sh`，
> 首次运行即报出 12 个错误（详见 D-025 与验收报告 §4.2）。

## D-020 服务器端口与资源隔离

- **决策**：本项目使用 Compose project `qinyang`，端口 MySQL `13316`、API `18110`、后台 `18111`，
  全部绑定 `127.0.0.1`；容器资源上限 MySQL 1C/2G、API 1C/1.5G、后台 0.5C/256M（合计 **2.5 核 / 3.75 GB**，
  满足「日常测试服务 ≤ 2.5 核 / 4 GB」）；日志 10MB×3 轮转。
- **理由**：目标文档要求「用独立 Compose project、端口、卷和专属测试库，不动其他项目」。
  服务器上已有 `nmg-pku-alumni`、`schoolwall` 等项目占用 18080/18081/18082、13306/13307、16379/16380。
- **影响**：管理后台与 API 通过 SSH 隧道访问，不直接暴露校园网。

## D-021 rsync 同步必须排除生成物

- **决策**：`infra/scripts/sync-to-server.sh` 排除 `node_modules/` `dist/` `images/`
  `catalog/products/` `media/` `.env` `.env.*` `coverage/`。
- **理由（实测教训）**：初次同步时 `rsync --delete` 曾把服务器上正在生成的 `media/` 目录
  与 `infra/docker/.env` 一并删除，导致媒体流水线中断且密钥丢失需重新生成。
  排除生成物与密钥是 rsync `--delete` 语义下的硬性要求。
- **影响**：服务器上的 `media/` 与 `.env` 由脚本自身管理，不随同步覆盖。

- **补充（收尾阶段实测）**：`--exclude='.env.*'` 会把 `.env.example` 一并排除在传输之外，
  服务器端该文件因此长期缺失（被排除的文件不会被 `--delete` 删除，也不会被补传）。
  修正方式是在排除规则**之前**加一条 `--include='.env.example'` ——
  rsync 的过滤规则「先匹配者生效」，模板文件因此正常同步，
  而真实的 `.env` 仍被排除且受 `--delete` 保护（rsync 默认不删除被排除的文件）。

## D-022 顾客端与后台共用同一套响应结构

- **背景**：小程序与管理后台分别独立开发，若各自约定返回结构，会出现「接口返回了但前端读不到」的静默缺陷。
- **决策**：
  - 图文说明页 `sections` 统一为 `{ id, title, description, items[], illustration, fieldCodes }`，
    `items` 为逐条要点，`description` 为段落说明 —— 小程序按此渲染，后台按此编辑。
  - `GET /measurement-templates/resolve` 同时返回 `templateId/templateCode/templateName/templateVersion`
    与 `id/code/name/version`，两种取法都成立，前端不必知道内部命名。
  - 小程序内保留一份 `types/contracts.ts` 契约副本（微信开发者工具无法编译工作区其他目录），
    由 `tools/sync_contracts_to_miniprogram.py` 同步；构建前用 `--check` 校验是否过期。
- **理由**：契约是三端的唯一事实来源，宁可返回值冗余，也不要让某一端读不到字段。
- **影响**：契约副本过期会导致构建失败（已加入 `build.sh` 的前置检查），不会静默失配。

## D-023 容器化部署的三处修正：网络端点、健康检查、媒体只读挂载

- **背景**：收尾阶段把 API 与管理后台也跑进 Compose 隔离栈时，暴露三个真实缺陷：
  1. `qinyang-api` 容器显示 Up，但运行时 `NetworkSettings.Networks = {}`、`Ports = {}`，
     容器内解析服务名 `mysql` 报 `getaddrinfo EAI_AGAIN`，18110 不可达；
  2. `qinyang-admin-web` 陷入 `Restarting (1)`，nginx 报 `host not found in upstream "api"`；
  3. 容器化验收 27/28，唯一失败项是商品主图 404。
- **决策**：
  1. **网络端点**：Compose 的 `depends_on` + `service_healthy` 只保证启动顺序，
     不保证端点 attach 成功。重建网络后旧容器会持有失效的 network id，
     因此**网络重建必须连容器一起完整销毁**（`docker compose down --remove-orphans`，含网络删除），
     再一次性 `up -d`，不允许在网络重建后复用旧容器。
  2. **健康检查**：API 增加容器级健康检查（镜像内无 curl/wget，用 node 内置 `fetch` 探测
     `/api/v1/health`）；管理后台的 `depends_on` 改为 `api: {condition: service_healthy}`。
     nginx 在**启动时**解析上游域名，上游不可用时是致命错误而非降级，
     因此「已启动」必须升级为「已健康」才能拉起依赖方。
  3. **媒体挂载**：新增 `STORAGE_MEDIA_ROOT` 配置项，把**可写存储根**（后台新上传）
     与**只读媒体根**（`tools/build_media.py` 产出的商品目录图）拆开，
     两者共用 `/static` 前缀 —— express 静态中间件默认 fallthrough，
     可写根在前（上传覆盖目录旧图），只读根在后兜底。
     容器内媒体目录以 `:ro` 绑定挂载，**不复制、不重建衍生副本**。
- **理由**：
  - 前两个缺陷都不是「配置写错」，而是「容器编排的隐含时序假设」，
    靠 `docker compose config` 展开结果无法看出，必须靠运行时 `docker inspect` 对照排查；
  - 第三个缺陷暴露出「开发模式把存储根与素材目录混用」的坏味道，
    容器化一旦把两者分离就会立刻暴露。显式建模两个根，比靠目录复用掩盖更安全。
- **影响**：
  - 抽取 `apps/api/src/common/static-assets.ts` 承载前缀推导与双根挂载，
    并新增 7 例单元测试锁定行为（含「无路径基地址必须回退 `/static`」这一真实踩坑）；
  - 容器化栈与独立进程模式各跑一轮 `acceptance.mjs`，**均为 28/28**；
  - 独立进程模式同步改为「可写 `storage/` + 只读 `media/`」双根布局，与容器一致。
- **复审**：正式部署接入对象存储后（`STORAGE_DRIVER=oss`），`STORAGE_MEDIA_ROOT` 语义需重新评估，
  届时商品图不再经本地静态目录对外提供。

## D-024 镜像构建阶段也遵守并发上限

- **背景**：目标文档对「图片批处理并发 ≤ 2」「测试并发 ≤ 2 Worker」有明确约束，
  但镜像构建阶段的 `pnpm install` 不受工作区的 `taskset` 保护 —— 它跑在 Docker 构建容器内。
- **决策**：两个 Dockerfile 统一设置 `npm_config_child_concurrency=2`、
  `npm_config_network_concurrency=2`，把镜像构建的子进程与网络并发也压到 2。
- **理由**：限核不能只覆盖命令行进程；`taskset` 对 docker build 内的构建步骤无效，
  必须在工具自身的并发参数上收紧，才能真正控制 CPU 峰值。
- **影响**：`qinyang/api:local` 构建约 4 分钟、`qinyang/admin-web:local` 约 2 分钟，
  两者串行执行，未与其他重型任务并发。

## D-025 量体模板：形状归一化 + 单一解析入口

- **背景**：本轮在小程序代码第一次被真正执行时，暴露出量体环节的一整条缺陷链：
  1. 原型数据是 snake_case（`section_id` / `measurement_fields` / `field_code`），
     契约要求 camelCase；种子把原型 JSON 原样入库，接口返回 `measurementFields: undefined`
     —— 顾客端表单渲染 0 个字段、提交空量体、服务端校验形同虚设；
  2. 解析接口按**分类**取模板、提交校验按商品**绑定**模板，两边不同源，
     顾客按 A 模板填表却被按 B 模板拒收；
  3. 客户端只接受数字 `code`，把服务端给出的业务错误码与真实原因全部丢掉，
     顾客只看到「服务器返回数据异常（HTTP 400）」。
- **决策**：
  - 新增 `apps/api/src/modules/templates/measurement-shape.ts` 作为**唯一**的形状归一化点：
    写路径（种子）先转换再入库并用 `assertSectionsUsable` 拦截空模板；
    读路径（模板 DTO、解析接口）统一归一化，历史 snake_case 行照样可用；
  - 新增 `TemplatesService.resolveForProduct(product)` 作为**唯一**的模板解析入口
    （优先商品显式绑定模板，其次按分类回退），**解析接口与提交校验共用**；
  - 客户端 `ApiEnvelope.code` / `ApiError.code` 放宽为 `number | string`，
    按后台 `http.ts` 的同一套语义透传服务端 message；
  - 小程序纳入类型检查（`pnpm typecheck:miniprogram`），并新增
    `tools/verify_miniprogram_flow.mjs`：用 tsc 编译小程序源码 + 注入 wx/Page 桩件，
    **在真实 API 上执行小程序自己的量体提交流程**。
- **理由**：
  - 三端各用不同的事实来源（集成测试自造模板、验收脚本从接口取、小程序从未执行），
    是这条缺陷链长期潜伏的根本原因 —— 验证必须落在**同一份真实数据**上；
  - 「表单渲染的模板」与「校验用的模板」必须是同一个对象引用来源，
    否则任何一端改动都会造成顾客无法提交；
  - 归一化点唯一化，比在每个消费点各写一次转换更不容易漏。
- **影响**：
  - 量体环节首次真正跑通：验收新增「模板带得出字段」「快照带回真实量体数值」两项断言；
  - 防回归层次：单元 8 例 + 集成 6 例 + 端到端 20 项断言；
  - 小程序类型检查纳入 `build.sh`，17 个页面不再游离于类型检查之外。
- **复审**：若商家要求量体模板改用其他建模方式（例如独立的量体字段表），
  则 `measurement-shape.ts` 应替换为查询层实现，`resolveForProduct` 的入口位置保持不变。

## D-026 分类层级语义 + 页面级执行验证作为常规关卡

- **背景**：页面级执行验证（把小程序 17 个页面在 Node 中跑起来打真实 API）
  连续抓出两个此前完全没人发现的缺陷：
  1. **分类层级语义错位** —— 商品挂在二级分组上，而小程序分类页默认按一级分类 id 查询，
     API 的 `categoryId` 又是精确匹配 → 顾客打开分类页看到的是**空列表**；
     分类树的 `productCount` 同样只统计直接挂载，一级分类恒为 0 件。
  2. **商品详情拿不到量体模板名** —— 契约声明了 `measurementTemplateName`、
     小程序页面也渲染它，但 API 侧把它硬编码成 `null`。
- **决策**：
  - `categoryId` 过滤改为**包含下级分组**（传入分组 id 时行为不变，因为分组没有子级）；
  - 分类树的 `productCount` **向下汇总**（一级分类 = 自身 + 所有下级分组）；
  - 商品详情按 `measurementTemplateId` 关联查出模板名称并返回；
  - 页面级执行验证（`tools/verify_miniprogram_pages.mjs`）与写路径执行验证
    （`tools/verify_miniprogram_flow.mjs`）**作为常规关卡保留在仓库里**，
    与契约核对、静态自检并列，由服务器执行。
- **理由**：
  - 「分类」在商家心智里是包含下级的，而商品实际挂在末级分组；
    过滤与计数若只认直接层级，顾客侧与商家侧看到的就不是同一个分类体系；
  - 静态检查只能证明「结构对」，执行才能证明「页面真的把数据渲染出来了」；
    本轮两个缺陷的共同特征是——接口 200、类型全绿、验收全绿，唯独没人跑过页面。
- **影响**：
  - 分类页从「0 件」变为正确展示；一级分类计数从 0 变为真实值；
  - 商品详情页能告诉顾客「按哪套量体模板测量」；
  - 新增集成测试「分类层级语义」4 例锁定上述语义；
  - 小程序 17 个页面首次全部在真实 API 上执行过，顾客侧的提交量体、
    确认报价、取消申请均由页面自身方法完成（53/53 断言）。
- **复审**：若商家把分类改成扁平结构（商品直接挂一级分类），
  本决策的「包含下级分组」逻辑仍然成立（没有子级即精确匹配），无需改动。

## D-027 后台页面级执行验证（读路径 + 写路径）纳入全量流水线

- **背景**：D-026 把「页面级执行验证」确立为常规关卡，但只覆盖了小程序侧。
  管理后台的 9 个视图 + 框架布局此前**同样从未在运行时执行过**，
  只被 `vue-tsc` 与 lint 检查过。本轮补齐时发现两类问题：
  1. **验证装置本身不成立** —— `@vue/compiler-sfc` 的 `compileScript` 产物仍是 TS+ESM，
     直接求值会抛 `SyntaxError: Unexpected token ':'`；
     `tsc` 的 `rootDir` 又被 `@qinyang/contracts` 顶出 `apps/admin-web/src`，
     导致编译产物目录结构与源码对不上。
  2. **断言形态与页面真实暴露的绑定不符** —— 例如 `can` 在所有视图里都是
     **函数** `can(key)` 而非权限映射；仪表盘字段是 `publishedProducts` / `draftProducts`
     而非 `published` / `draft`；模板「已发布」态在契约里是 `ACTIVE` 而非 `PUBLISHED`。
- **决策**：
  - 抽出共享运行时 `tools/lib/admin-runtime.mjs`：
    `tsc` 编译 → `ts.transpileModule` 去类型 → `Module._load` 钩子统一桩件
    （`vue` / `vue-router` / `tdesign-vue-next` / `@qinyang/contracts` / `*.vue`）
    → 真调 `options.setup()` → 手动触发 `onMounted`；
  - 拆成两个脚本：`tools/verify_admin_pages.mjs`（读路径，55 项断言）与
    `tools/verify_admin_write.mjs`（写路径，53 项断言，覆盖
    审核 → 报价 → 顾客确认 → 建单 → 推进状态 → 发货）；
  - 两个脚本**纳入全量流水线** `infra/scripts/build.sh`：
    流水线用**本次构建产物**在 18112 端口起一个独立 API 进程
    （不打扰预览用的 18110/18111 容器栈），再让四套页面级执行桩打这个真实实例；
  - 断言一律对齐**页面真实暴露的绑定**，不为通过而放宽；
  - 验证数据卫生：验证商品没有删除接口（商品只做下架归档），
    因此收尾统一「下架 + 排序推到末尾（9999）」，避免挤占商家真正要看的列表头部，
    并对历史遗留的验证商品做同样的自愈。
- **理由**：
  - 写路径才是商家体验的主体：读路径能证明「看得见数据」，
    写路径才能证明「用得动后台」；
  - 流水线必须**跑本次构建产物**，否则验的是旧镜像，流水线就成了摆设；
  - 断言写错（例如把 `can` 当映射用）会制造「假红」，
    让人习惯性忽略失败项 —— 这比没有验证更糟。
- **影响**：
  - 后台 9 个视图 + 布局首次全部在真实 API 上执行过（读路径 55/55）；
  - 商家的完整动线首次由**页面自身的方法**跑通（写路径 53/53）：
    新建/编辑/上下架商品、增删改分类、增删轮播、新建并发布量体模板、
    审核申请、报价（含金额校验拦截）、建单、推进状态、填写物流发货；
  - 全量流水线从「静态检查 + 单元/集成测试」升级为
    「静态检查 + 类型检查 + 单元/集成测试 + 四套页面级执行验证」；
  - 后台接口基址新增唯一为可测性开的后门 `globalThis.__QY_API_BASE__`
    （生产构建下不存在，行为与原来完全一致）。
- **复审**：若后台改用 Pinia 持久化插件或 vue-router 的真实实例，
  `tools/lib/admin-runtime.mjs` 的桩件部分需相应更新；
  断言部分与页面实现无关，不受影响。
