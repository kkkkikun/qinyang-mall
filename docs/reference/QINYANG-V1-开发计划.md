# 琴扬精纺羊绒｜微信商城 V1 开发计划

基线：`qinyang_customer_demo_v2_pixel(1).html`。原型确认了页面和交互，不确认商品价格、下单、客服、支付规则。建议先做独立的体验版，不动旧店线上版本。

## 1. V1 做什么

- **看货**：首页、羊绒衣橱自动轮播和手滑、搜索、分类、详情、商品分享。保留原型的品牌识别、分类左右栏、卡片比例、间距和动效；Windows 的 390×844 手机框只用于审稿。小程序使用真机安全区、微信原生胶囊和分享，不移植 iframe、HTML 内嵌图片或假胶囊。空搜索、图加载失败、下架商品均有可用退路。
- **量体与交易**：保留购物车、个人中心、我的订单入口。上装和长裤分开使用模板、校验厘米单位；量体内容在定制申请里提交，不在购物车列表公开。洗护、材质说明先做可维护的图文，不做材质配置器。原型里的“客服聊天”落地为微信客服入口，不自建聊天。
- **店员后台**：商品和分类、图集和首页轮播、上下架、订单与量体资料、报价、发货和退款处理记录；店主/店员分权，改价与订单操作有审计。先用 10–15 个已获授权的代表性商品跑通，再按 SKU 批量导入其余已整理商品。导入先预检，问题行可重跑；没有确认价格的商品不自动上线。公开图走对象存储，源图备份，列表用缩略图。AI 上身图不阻塞 V1，获授权并经商家对照实物确认后再补。
- **不做**：多商户、积分、储值、礼卡、付费会员、复杂促销、自建即时聊天。未确认存在的颜色规格、库存和现货业务，不先做成复杂 SKU 系统。

### 推荐交易规则

默认定制单走 **提交量体 → 店员确认并报价 → 顾客确认报价 → 支付（如启用）→ 制作 → 发货 → 完成**。定制单首期一次一个款式；购物车负责暂存选款，不强行做定制和现货混合结算。只有店主确认确有固定价可直接售卖的商品，才加固定价下单分支。确认后冻结商品、报价、量体模板及订单快照，修改应走重报价并留痕；不要直接改已支付金额。

D1 让店主选清楚：V1 **是否线上收款**，若收款是**全款还是定金**、尾款怎么结、运费/周期/取消退款谁核准。默认开发时先不打开真实支付，由 `PaymentGateway` 假实现走通。只选一条收费路径，定金与尾款不要硬套进同一笔支付。若商家选择仅询价，明确页面是定制申请，不显示假的已支付、可退款状态。正式支付上线是单独验收门，不把演示版当正式商城。

## 2. 技术栈

| 层 | 首选 | 为什么 |
|---|---|---|
| 顾客端 | 微信原生 WXML + WXSS + TypeScript，Windows 微信开发者工具 | 只做微信端，直接用 swiper、登录、分享和支付，对照原型逐屏复刻；暂无跨端需求，不上 Taro/uni-app |
| 后台 | Vue 3 + Vite + TypeScript + TDesign Vue Next | 复用你已用过的表格、表单和操作习惯 |
| API | Node.js 24 LTS + NestJS + TypeORM；REST、OpenAPI | 单体按 catalog、quote/order、payment、admin/media 分模块；沿用熟悉的校友会技术路线，不复制其数据、密钥、重型部署配置 |
| 数据与部署 | MySQL 8.4 LTS + 对象存储，Docker Compose + Nginx/HTTPS | 数据库管交易一致性；对象存储管图片；先不用 Redis/MQ/ES，按部署压测再加 |

仓库建议：`apps/miniprogram`、`apps/admin-web`、`apps/api`、`packages/contracts`、`infra`、`docs`。后台和 API 用 pnpm workspace，原生小程序先无运行时 npm 依赖，跨端只共享 API 契约或生成的类型，不把 Node 包一起打进小程序。金额用整数分；支付和退款单独记录，交易状态不得由前端报成功后直接更新。

## 3. 你本地改，学校服务器构建

- **Windows/WSL**：Git、Agent、编辑、原生微信开发者工具预览与 iOS/Android 真机。小程序项目放在 Windows 与 WSL 都可访问的同一份工作区；如果 DevTools 对 WSL 路径不稳定，优先用 Windows 盘目录或同步可预览产物。平日可用本地 mock；后台通过服务器隔离测试栈做联调。无需把 MySQL 或重型 Docker 构建装到笔记本。
- **学校服务器**：走你现有 SSH 通道，从私有仓库构建指定 commit，负责 pnpm 锁定安装、类型检查、单测/集成测试、后台构建、API 镜像、批量图片处理。Node、pnpm 和 lockfile 纳入版本控制；Linux 上安装 Linux 依赖，不传 Windows 的 node_modules。构建前核对出网、Docker 权限、磁盘配额和目标架构。用独立 Compose project、端口、卷和专属测试库，不动其他项目；管理/API 默认不对校园网公开，桌面联调用 SSH 转发。本地有未提交改动时先提交到私有开发分支或走明确的补丁同步，不从工作目录隐式发布。
- **交付产物**：每次构建输出 commit SHA、日志与测试结果、后台静态包和带 SHA 标签的 API 镜像；保存上一版本及数据库迁移、备份、恢复说明。首期体验版由 Windows DevTools 上传；需要自动化上传再评估官方 miniprogram-ci、上传密钥和 IP 白名单，构建任务不默认上传或发布。
- **线上**：学校服务器只作构建/测试，不接真实支付回调、不存真实量体数据。正式环境单独用商家获授权的公网主机、HTTPS 域名与对象存储；真机联网联调用合规测试域名，不依赖本机跳过域名校验。密钥只留在授权运行环境。开发、联调、生产分开配置，不共用业务数据。

## 4. 排期（单人 + Agent，约 15–20 个有效开发日）

示例从 11 月 30 日起排，按实际开工平移。以下是工程目标，不是对客户承诺的正式上线日。

| 阶段 | 示例日期 | 完成标志 |
|---|---|---|
| P0 冻结范围与跑通构建 | 11/30–12/2 | 归档 HTML 与关键页面截图；核对 AppID 管理权、旧支付商户号、旧订单和量体记录可否导出；搭好隔离测试栈；指定 commit 可构建、空白原生项目能预览 |
| P1 顾客端 + 商品后台 | 12/3–12/11 | 首页轮播、搜索、分类、详情在两种设备核图；店员在后台新增/上下架商品后顾客端可看到变化；样本商品可导入 |
| P2 完成定制闭环 | 12/14–12/18 | 用户提交量体、店员报价、用户确认、后台更新制作/发货、用户查看订单；按确认规则接假支付或真实支付适配器；关键状态测试全过 |
| P3 体验版、验收与提审准备 | 12/21–12/25 | Android/iOS 真机验收、商家体验、独立备份恢复演练；若真实收款已具备条件，验证回调、查询、退款与发货，再进入提审 |

若旧 AppID 有权限且可按合同使用，优先体验版验证，保留旧店入口的机会更高，但旧门店码、旧商品分享卡、历史订单**不会因沿用 AppID 自动迁移**。上线前让商家选一个旧二维码、一张旧分享卡、一笔已付未完成的定制单做只读核验，明确旧单售后责任。若原账号不可用，则新 AppID、主体认证、类目及备案、合法域名、支付开通和审核单独排期；不因其中一个审批未完成而停掉模拟开发，也不先承诺切店时间。

## 5. 发布门槛

1. 手机端：Android 和 iOS 截图逐屏对照；轮播、分类、搜索、退回和分享链路没断。价格变动、商品下架、断网、失败重试与重复点击都有反馈。
2. 交易：服务器验报价与订单归属；支付通知验签、校验订单与金额及幂等，缺通知时查单补偿；覆盖重复通知、取消、退款结果和发货。按商家类目确认微信发货信息管理要求。真实订单、支付与退款仅在商家授权后做。
3. 数据：量体、地址、联系方式按必要范围采集，权限隔离，不写入普通日志；演练恢复一笔假订单和其图片引用。保留旧版本和停收新单开关，先小范围试用再切换生产。

## 给本地 Agent 的第一阶段任务

读取本计划和 `qinyang_customer_demo_v2_pixel(1).html`，保留 HTML 作为设计验收基线。从当前分支先检查已有文件与未提交内容，不覆盖既有成果。初始化独立项目，让 Windows DevTools 能预览原生小程序，让学校服务器对一个固定 commit 跑通锁定依赖安装、检查、测试和构建。做一个真实的最小垂直切片：后台创建/上架一款商品 → API 提供列表与详情 → 小程序首页点进详情并显示正确图片和报价状态。先用假数据、假支付。交付预览步骤、构建命令、测试记录和任何平台阻塞；禁止自动购买、上线、上传客户旧数据、领取支付密钥或更改旧商户账号。
